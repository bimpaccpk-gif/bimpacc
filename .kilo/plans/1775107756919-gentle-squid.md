# Device Lock Feature Plan

## Overview

Lock student accounts to their first login device. Once a student logs in from a device, subsequent login attempts from different devices are blocked. Students can use different browsers on the same device. Admins can reset a user's device binding.

## Approach

Use **FingerprintJS** (open-source, `@fingerprintjs/fingerprintjs`) for browser-based device fingerprinting. It generates a stable hash from hardware-level signals (GPU, screen, CPU cores, OS, etc.) that are consistent across browsers on the same device.

---

## Step 1: Database Migration

Create migration `024_device_fingerprint.sql`:

- Add `device_fingerprint TEXT` column to `public.users` table (nullable)
- Add `device_locked_at TIMESTAMPTZ` column to track when the lock was set

## Step 2: Install FingerprintJS

```bash
npm install @fingerprintjs/fingerprintjs
```

## Step 3: Modify Login Server Action (`app/actions/auth.ts`)

Update `signIn` action to accept a `device_fingerprint` field from the form data:

1. After successful `signInWithPassword`, fetch the user's `device_fingerprint` and `role` from the `users` table
2. **If user is a student:**
   - If `device_fingerprint` is NULL (first login): store the submitted fingerprint + set `device_locked_at = now()`
   - If `device_fingerprint` is NOT NULL: compare with submitted fingerprint. If different, return error `"This account is locked to a different device."`
   - If role is NOT student: skip device check entirely (admin/instructor unrestricted)

## Step 4: Modify Login Page (`app/(auth)/login/page.tsx`)

1. Load FingerprintJS on page mount, generate the visitor ID
2. Store the fingerprint hash in state
3. Add a hidden `<input name="device_fingerprint">` to the login form
4. Set its value to the generated fingerprint before form submission
5. Show a loading state while fingerprint is being generated
6. Display a clear error message if device mismatch is detected

## Step 5: Admin Device Reset

### 5a: Server Action (`app/actions/admin.ts`)

Add `resetDeviceFingerprint` action:

- Verify admin role
- Set `device_fingerprint = NULL` and `device_locked_at = NULL` for the target user
- Only reset if target user is a student

### 5b: Admin User Detail Actions (`components/admin/user-detail-actions.tsx`)

Add a "Reset Device Lock" button (visible only for student users who have a device fingerprint set). Uses the `resetDeviceFingerprint` server action with `useActionState`.

## Step 6: Protect Session-Level Bypass

In `proxy.ts`, add device fingerprint validation for authenticated students on protected routes:

- Fetch `device_fingerprint` along with `role` and `is_paused`
- If role is student and `device_fingerprint` is set, check for the fingerprint cookie/header
- **OR** skip proxy-level check and rely solely on login-time check (simpler, recommended)

**Decision: Login-time check only.** The device lock is enforced at login. Once a session cookie is issued by Supabase, it remains valid until expiry. The lock prevents new sessions from different devices. This is simpler and avoids complexity in the proxy.

## Flow Diagram

```
Student Login:
  1. Login page loads → FingerprintJS generates device hash
  2. User submits email + password + device_hash
  3. Server validates credentials
  4. If student:
     a. No stored fingerprint → save hash, allow login
     b. Stored fingerprint matches → allow login
     c. Stored fingerprint differs → return error "Account locked to another device"
  5. If admin/instructor → skip device check, allow login

Admin Reset:
  1. Admin views student in user detail panel
  2. Clicks "Reset Device Lock" button
  3. Server clears device_fingerprint and device_locked_at
  4. Student can now login from a new device (re-locks on next login)
```
